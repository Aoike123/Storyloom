# 分镜视频存储规范 v1

日期：2026-09-13。状态：独立视频入库、素材快照、帧级选用及原版发布清单已实现；分支清单与懒加载调度仍为后续设计。现有视频不批量搬移。与[可替换故事线设计](rejoinable-storyline-design.md)配套。

## 本轮已实现

- `backend/video_files.py`：用现有 FFmpeg 探测实际帧数、帧时间、编码、尺寸和音轨；保留源文件，必要时重封装/转码；提取实际选区图片。播放版当前固定 24 fps，项目级自定义帧率尚未开放。
- `backend/video_storage.py`：登记文件摘要与稳定引用，保存图片资产和分镜版本快照、ClipArtifact、ClipUse，导出不可变发布清单。数据库为权威来源。图片快照当前支持 PNG/JPEG/WebP；独立声音资产版本仍待后续声音模块实现。
- 作者制作流程的新视频任务自动入库。审片保存独立选用记录，发布保留 start/end 兼容字段并增加 use_id、occurrence_id、帧范围和边界图。作者审片界面展示选区入画和出画图片。
- 完成下载或保存源文件后中断，可继续媒体登记，不重复收费提交。恢复前核对本地文件和来源；正在等待的供应商任务不会被静默切换到另一个端点。
- 旧发布继续按原路径、原秒数读取；仅在主动登记或新审片时补信息。历史事件时间保持待帧级复核，不自动宣称精确。
- 作者主流程使用已冻结的本地图片，输入快照只保存可审计引用。任何原始密钥都不进入素材或发布记录。

本轮验证：89 项后端测试通过，TypeScript 类型检查通过。新增检查使用本地生成的测试视频和真实 FFmpeg，覆盖有声视频、源文件保留、Range 下载、准确边界帧、非标准编码、可变帧率、非零起始时间、素材历史、文件变更拦截、发布兼容与中断恢复；模型服务由测试替身代替，未发起收费调用。运行中的 API 和执行器需要重新加载代码后启用新流程。

| 接口 | 用途 |
| --- | --- |
| `GET /api/clips/{clip_id}/storage` | 读取素材登记与当前选用区间 |
| `GET /api/reader/releases/{release_id}/manifest` | 读取发布清单 |

发布 JSON 快照写入 `data/manifests/releases/{release_id}/v{revision}.json`，缺失时可通过同一发布请求从已提交数据库记录恢复。动态分支、pending 槽位以及实时播放通知尚未接入，本轮不会因此开始生成读者改写视频。

## 建议确定的格式

采用“独立视频文件 + 结构化分镜与素材记录 + 带版本的播放清单”。视频编码负责播放，分镜记录负责身份、因果和一致性，播放清单负责顺序、选取区间与分支。三者独立引用。

一次生成的素材与一个叙事分镜不是固定一对一：一镜可以重试生成多个候选，一段素材也可以被多处清单引用。新生成获得新 clip_id；修改分镜增加 shot_revision；调整剪辑区间产生新 use_id。数组下标不承担这些身份。

## 1. 视频文件

| 项目 | v1 约定 |
| --- | --- |
| 供应商原始结果 | 保存实际返回的原始文件，按探测到的容器确定扩展名，不直接把任意返回内容改名为 MP4 |
| 浏览器播放版本 | MP4 容器，H.264/AVC 视频，yuv420p；存在音轨时使用 AAC-LC |
| 音频 | 播放版目标 48 kHz 双声道；源文件无音轨时明确记为无音轨，不声称已有配音；保存原有声音 |
| 提前开始下载播放 | 普通 MP4 启用 faststart，并验证媒体服务的 Range 请求；不等整部作品下载 |
| 帧率 | 播放版本采用项目级恒定帧率，v1 默认 24/1 fps；每个素材记录实际探测值 |
| 画幅和尺寸 | 在作品制作配置中确定，保存精确宽高；保持比例，不把所有作品强制成横屏，不盲目放大小分辨率素材 |
| 参考图片 | 关键帧、实际剪辑边界帧保存 PNG；列表封面可另存 WebP/JPEG |
| 可选交付版本 | 后续从播放素材生成 fMP4/HLS 等传输版本，继续引用同一素材身份 |

MP4 只是容器，仍需明确内部编码。H.264 与 AAC 的 MP4 是适合本项目首版浏览器播放的兼容性选择。[MDN 容器说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)、[MDN 编码说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)。

faststart 将普通 MP4 的索引移到文件前部，有利于开始播放；它不是供应商生成过程中的媒体流。普通 faststart MP4 与分片 MP4 作为不同播放版本处理，不盲目组合参数。[FFmpeg 格式说明](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv)。

符合播放规格的原始结果可以直接复用同一文件；只需移动索引时重封装，编码或帧率不兼容时才转码。原始结果保留，避免重复有损转码。归一化耗时计入片段可播放延迟，不假设免费或瞬时完成。

## 2. 数据对象与不可变边界

| 对象 | 保存内容 | 修改方式 |
| --- | --- | --- |
| ShotRevision：分镜版本 | story_id、shot_id、revision、剧情目的、预期事件、入口/出口条件、回归候选、素材快照 | 新增版本，历史版本保留 |
| ClipArtifact：生成素材 | clip_id、分镜来源、供应商/模型/任务、实际生成输入的引用、原始及播放文件、摘要、媒体实测属性 | 完成登记后不覆盖；重新生成获得新 ID，新增播放规格获得新文件记录 |
| AssetRevision：素材版本 | 角色、服装、场景、道具、声音的 asset_id/revision、不可变文件引用与 SHA-256 | 新增版本，不只改一条记录的版本数字 |
| ClipUse：一次选用 | use_id、clip_id、使用的播放文件 ID、分镜版本、入点/出点、实际边界帧、事件标注版本 | 调整选取区间产生新 use_id，不裁坏源文件 |
| StoryRelease：原版发布 | release_id、精确分镜与素材版本、原版顺序、回归节点与依赖 | 发布快照不可变，新发布生成新版本 |
| BranchManifest：分支清单 | session_id、branch_id、revision、base_release_id、已看前缀、新片段槽位、回归位置 | 生成下一版本，旧清单保留 |

剧情“预期事件”与“画面已验证事件”分开。审核或事件时间修正产生独立标注版本，由 ClipUse/发布快照引用；不能修改不可变视频文件，也不能把提示词当作画面事实。

素材绑定至少包含语义角色（角色/服装/场景/道具/声音）、asset_id、revision、实际引用文件 ID 和摘要。仅记录“女主角图片”或引用可变的最新 URL，无法重现旧镜头。

回归节点另存条件与依赖，不把回归成功写成视频文件的固有属性。同一片段能否复用，要结合当前剧情状态判断。

## 3. 文件布局与数据来源

本地布局示意，ID 仅为示例：

```text
data/
  media/
    clips/
      clip_abc/
        source.mp4                 # 扩展名以真实容器为准
        playback_v1.mp4            # 如 source 符合规格，可引用同一文件
        poster.webp
    clip_uses/
      use_abc/
        in_frame.png               # 所选区间的第一显示帧
        out_frame.png              # 所选区间的最后显示帧
    assets/
      asset_abc/
        r1/reference.png
        r2/reference.png
  manifests/
    releases/release_abc/v1.json
    branches/branch_abc/v1.json
    branches/branch_abc/v2.json
  story.db
```

数据库是运行时结构化记录、任务状态和当前清单指针的权威来源；JSON 文件是由数据库生成的不可变快照/导出件，不允许手工改 JSON 再与数据库双向同步。发布和分支快照都带 schema_version；结构升级不静默改写旧版本。

数据库保存稳定文件 ID、相对存储 key、字节数、MIME 和 SHA-256。浏览器访问 URL 在响应时解析；供应商临时下载地址、签名地址不作为永久素材位置。未来迁移对象存储仅替换 key 的解析方式。

不把完整视频、图片 Base64 放进数据库。相同文件可按摘要去重，但内容相同不代表业务上是同一镜头，也不代表剧情状态允许复用。

## 4. 时间坐标与首尾帧

新播放版本按恒定帧率记录 frame_count，并使用整数帧范围 `[in_frame, out_frame)`：入点包含、出点不包含。帧坐标基于指定 playback 文件，从零开始。时长由帧数与帧率计算，不把小数秒作为唯一长期坐标。

例：一个 24 fps、120 帧的 5 秒素材，只选 1–4 秒：

```json
{
  "schema_version": 1,
  "use_id": "use_abc",
  "shot": {"story_id": "story_abc", "shot_id": "S03", "revision": 2},
  "clip_id": "clip_abc",
  "playback_file_id": "file_playback_abc_v1",
  "range": {"in_frame": 24, "out_frame": 96},
  "boundaries": {
    "first": {"frame_index": 24, "file_id": "file_in_abc"},
    "last": {"frame_index": 95, "file_id": "file_out_abc"}
  },
  "annotation_revision_id": null
}
```

实际使用时长是 72/24 = 3 秒；衔接参考取第 24 帧和第 95 帧。不能拿整段素材的第 0 帧和第 119 帧作为这次选用的边界，也不能对 out_frame 再取图，因为它已经不属于选区。

UI 可继续显示秒，兼容响应可由帧坐标派生 start/end。源视频若是可变帧率，先保留源时间戳和归一化映射，事件标注绑定归一化后的播放文件。不能简单用“源秒数 × 24”伪造映射。视频帧与音频采样存在不同时间基，剪辑时按同一时间轴同步处理，不单独累加取整后的镜头秒数。

## 5. 分支与懒加载的存储表示

原版素材只存一份。分支清单引用已看过的原版选用项、新生成项以及后续可复用项；相同视频引用不再复制文件。一个素材在同一清单出现多次，用独立 occurrence_id 区分每次出现。修改使用分支版本和稳定位置，不能只传“第几个片段”。

清单的槽位分成两类：

- ready：持有已经满足当前发布/播放检查要求的 use_id，允许进入播放器。
- pending：持有 task_id、分镜版本、分支版本和依赖；尚无可播放文件。细分进度从任务记录读取。

任务完成不直接修改旧快照。服务端确认分支版本、素材版本与质量状态后生成新清单，并以版本比较更新当前指针。旧回包不得覆盖新分支。

播放器只消费连续就绪的前缀。B01 ready、B02 pending 时允许先播 B01，但不得越过 B02 播到后面与剧情不兼容的原版。回归候选只有条件得到验证后才进入可播放的连续路径。视频已下载与业务上可播放是两个状态。

已观看内容固定到具体 occurrence_id 与片内帧位置；再次改写保留前缀。若在镜头中途切出，为保留部分建立新选用项并记录实际切出帧，源文件不变。分支可以再次分支，记录父分支及版本；最终清单仍能解析成明确的视频引用序列。

## 6. 写入、校验与兼容现有文件

新素材按“任务输出临时文件 → 文件完整性/媒体属性检查 → 必要的播放版本准备 → 摘要及引用登记 → 质量检查 → 可播放”推进。部分下载文件不能暴露为 ready。文件与数据库没有天然的跨介质事务，需使用同卷原子改名、幂等登记和恢复检查；崩溃后可继续登记已有文件，不盲目重复收费生成。

每次引用至少校验：文件存在、摘要匹配、播放规格符合该项目、`0 <= in_frame < out_frame <= frame_count`、边界帧对应正确播放文件、素材版本可解析、分支版本仍有效。未知的事件状态和画质检查保持未验证，不自动补成通过。

现有文件采用渐进迁移：先为平铺的 data/media/*.mp4 补登记，仍引用原路径；不先批量搬移或转码。保留旧发布清单和 start/end 秒坐标的读取能力。需要生成 v1 选用项时再探测实际媒体、定位剪辑帧并生成边界图，旧版秒数在完成定位前不能直接宣称帧级精确。

当前代码已有的 clip_id、shot_id、source_task、素材版本和 reader_trim 可以作为迁移来源。现有真实视频记录仍缺文件摘要、完整编码属性、不可变资产历史、独立选用项和实际剪辑边界图，需补齐。审核状态已经使用 Record.version 变化，不能直接将它与新设计的 shot_revision 或不可变媒体版本混为一谈。

## 下一步改造范围

1. 增加统一的 ClipArtifact/ClipUse 登记与读取路径：新生成、上传和兼容旧素材都走它。
2. 增加媒体探测、文件摘要、必要重封装/转码及选用边界帧提取。
3. 生成任务保存真实分镜、素材版本和输入引用；失败保留任务号及已取得的文件。
4. 发布清单绑定不可变选用项，同时保留当前播放器的 start/end 兼容字段。
5. 在上述基础上再加入 ready/pending 分支清单、逐镜通知和回归调度。

这一阶段不需要重生成整部视频，也不需要先完成 HLS。首先让每个已生成片段具备可追溯身份、稳定文件、准确选区和素材关联。
