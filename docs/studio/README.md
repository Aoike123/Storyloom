用户确认设计通常只需看产品规范与交互稿。主模型读取架构、计划和账本；轻量执行器只收到一张已就绪任务卡、必要契约摘录与绝对路径白名单。

## 文件分工

```text
docs/studio/
├── README.md                 当前入口与阅读路径
├── product/                  产品规则
├── architecture/             工程结构、领域契约、待冻结决定
├── execution/                实施顺序、分批任务、派发模板、验收账本
├── evidence/                 实现核对与有基线的验收证据
├── prototypes/               设计稿
└── archive/                  已停止生效的资料
```

不用日期目录、D/F/A 批次或旧入口名称区分“哪个设计最新”。日期用于证据、变更记录和归档，当前文件使用稳定路径并原地更新。

## 状态与冲突处理

产品规则已合并为规范；架构总体边界已写清，详细 schema/API、剪辑内核和供应商/对话执行协议仍须 ROOT-02/03/04 冻结。重构应用代码尚未开始。ROOT-05 只读盘点已验收，不代表任一制作能力已实现。

实际任务状态只写入账本；产品规范不写“前端完成”，架构文件不写“已上线”，任务卡不复制进度表。旧 F0–F4、A1–E、D09 的完成声明留在历史档案。

旧后端workflow、节点绑定、阶段验证器及专用测试已退出实施标准；它们只可用于历史核对或经过重新审定的基础设施提取。新流程从当前产品规则重新定义，不以旧管线能运行作为验收条件。

用户最新决定优先。产品行为由产品规范定义，工程落实由架构契约定义；发现冲突先由主模型修正规范或契约并标记受影响任务，执行器不能任选一份。交互稿未覆盖的能力按规范执行；归档文件不得覆盖当前规则。

## 更新步骤

1. 用户交互或产品范围改变：更新产品规范对应规则及变更记录，再更新必要设计稿。
2. 数据、接口、模块或内核改变：更新相应架构文件和决策版本，列出影响的任务。
3. 主模型调整任务卡/账本并重新定就绪状态；轻量模型只实现已冻结的一项。
4. 主模型独立验收并记录代码基线、验证与证据；通过后再派后继任务。

同一规则不再另写“方向补丁”或第二份“最新计划”。新增文档先确定所属层和职责，再从此入口或相应批次索引链接。
