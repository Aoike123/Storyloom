# Storyloom 全面重构原子实施与验收计划书

版本：2.2 · 2026-10-13。方向：**彻底重构，旧版本退役。** 基础框架、数据模型和大部分来源操作已验收；实际执行与验收统一见[任务账本](acceptance-ledger.json)。

本版为全面重构计划。根据用户最新决定，从已确认的设计建立新模型、新服务、新工作台和新生产/剪辑/对话链路，最终清除旧产品代码和入口。旧实现只供识别问题和可提取基础设施，不成为新流程约束。旧后端workflow、节点绑定、提示词契约及专用测试均退出标准；ROOT-02/04从当前产品规则重新定义新命令与生产/对话流程。

## 1. 最终交付及依据

一条真实、可恢复的路径：新建项目 → 导入原文 → 在连续阅读区划出荧光区域 → 保存候选/确认片段 → 剧本动作与对白 → 分镜与共用资产 → 生成/审核视频 → 左侧资源取用与全屏剪辑 → 确认同一剪辑版本 → 发布/导出。每步骤都有对象属性、实际任务状态和可恢复自然语言对话。

- 左侧原文/动态故事片段两视图；一个连续非空区域就是一个片段，候选和确认都不可重叠，允许相接。原文不插入片段卡片或状态。
- 切分、剧本、分镜、资产都是无限画布，自由拖动/平移/缩放；坐标不改变业务归属、顺序或版本。
- 剧本连线从整块高亮的实际边缘发出，一个起点和主干再分支到动作/对白。资产出现位置关联实际项目资产及版本，允许共用。
- 成片是占满主工作区的剪辑组件，左侧就是资源区；浏览/预览资源保留时间轴，明确插入产生独立实例。
- 属性对应选中的真实对象，步骤对话固定在工作区底部；不要求标出agent/model名称。

设计依据：[产品规范](../product/product-spec.md)、[确认稿](../prototypes/source-studio.html)。问题依据：[核对报告](../evidence/implementation-audit-2026-10-04.md)。技术依据：[项目结构](../architecture/project-structure.md)、[领域契约](../architecture/domain-contracts.md)。派发格式：[执行器提示词](executor-prompt.md)。

## 2. 实施基线与新架构

当前工作目录为 `/mnt/Code/agent-orchestration/workflow/Storyloom`。派发前主模型核对实际 checkout、HEAD、工作树和隔离运行配置，将准确目录与基线写入派发单；账本中的旧机器路径和历史受测基线只用于追溯，不直接作为当前启动命令。不得在不同 checkout 交错修改同一任务。

新边界：

| 区域 | 本轮新建位置/入口 |
| --- | --- |
| 工作台 | `/studio/[projectId]`；`web/features/studio/` |
| 项目首页/公开详情/观看 | `/`、`/projects/[projectId]`、`/watch/[releaseId]`；新组件消费新API |
| 领域服务、模型、任务、会话、媒体 | `backend/studio/`；API统一 `/api/studio` |
| 测试与fixture | `tests/studio/`、`web/tests/studio/`、`tests/fixtures/studio/` |

任务卡使用完整仓库相对路径；每次派发必须展开为实施目录下的**绝对路径**。模块归属和依赖方向只在[项目结构](../architecture/project-structure.md)维护，不在任务卡另建目录规则。新文件尚不存在，正是任务交付；不得转到旧目录找一个近似组件包装。

新代码可以复用批准的基础设施：框架、数据库连接/Base、账号鉴权、纯供应商协议/文件工具、主题语义。禁止依赖旧 author UI、旧workbench组件、旧Record业务内容/Task阶段、旧author_flow及旧业务API。数据模型是新领域表；同一业务归属只有一份权威。

用户已明确允许删除旧版代码，退役操作无需重复请求许可。代码退役指旧产品实现和路由；计划不安排清空已有数据库或批量删除磁盘媒体。新系统不承诺旧项目/原文引用/发布格式的迁移与兼容。新系统自身产生的revision与历史发布仍按设计保留真实依据。

## 3. 执行方式与原子边界

主模型负责架构、schema/API/状态、内核、供应商/agent执行权、拆任务、审diff、独立复验、返修、集成和最终签收。轻量模型（如gpt-6-luna）只实现已就绪的一张卡。

主模型统一派发，**项目不设置固定并行数量上限**，运行容量遵循用户配置的 Harness 限制。按独立就绪任务和可用资源安排并行，不为提高并行数量放宽依赖或拆出无意义任务。执行器每次只接一张叶卡，不再创建子代理。

并行派发必须满足：

1. 每张卡的全部依赖已由主模型标记 accepted，接口与契约已冻结。父卡不可派发；后继不能与尚未验收的前置任务同时实施。
2. 写入白名单互不重叠，包括实现、测试、fixture 和生成文件。同文件的不同函数也按冲突处理；共享 API 装配、schema、依赖清单或契约改动先单独验收。
3. 数据库、媒体目录、输出目录、端口及其他可变资源隔离；无法隔离的资源串行使用。全局构建、共享缓存和集成测试由主模型统一安排。
4. 派发单记录 task_id、执行目录、基线 commit、文件白名单、资源范围及同批并行任务。共享 checkout 时主模型保留文件归属记录，执行器只检查自己的白名单；其他任务产生的无关脏文件不构成自动阻塞。白名单内存在未分配改动或基线异常时先报告，不覆盖。
5. 执行器不得提交、切换分支、合并、重置工作树、修改账本或格式化白名单外文件。主模型在执行器停止写入后逐项审查、复验、提交和入账，提交只包含该任务的文件，不使用全量暂存。
6. 子任务 submitted/blocked 并停止后释放运行名额；主模型可派发另一项独立就绪任务。submitted 不等于 accepted；其依赖后继必须等待验收。发现接口或资源冲突时暂停受影响任务，重新划分白名单再继续。

每项仍遵循 `派发 → submitted → 主模型独立验收 → accepted`。集成导致其他执行器所见 HEAD 前移时，由主模型通知新基线；执行器核对前移提交未改动自己的白名单再继续，不自行接受影响本卡的改动。

每卡一个明确行为，原则最多3个实现文件加直接相关测试。模型不能顺手完成整个工作区、猜接口、改变导航、加兼容/迁移、升级依赖或重排无关代码。白名单不足由主模型进一步拆卡。任务中指定多个状态只是同一行为的成功/失败面，不能用此扩张业务。

状态：`planned → ready → running → submitted → accepted`，失败为rejected，契约未定为blocked_by_design。ready必须由主模型确认具体接口已冻结、白名单已收窄且依赖已验收；任务族父卡不可直接派发。依赖只认主模型accepted；构建通过、按钮出现、执行器说完成都不能代替验收。账本由主模型维护。

## 4. 批次和主模型门槛

| 批次 | 内容 | 退出条件 |
| --- | --- | --- |
| 0 | ROOT：目录/架构/内核/执行边界/旧依赖盘点 | 数据及模块契约可照单实现；代码、端口准确 |
| 1 | BASE、DB、SOURCE | 新项目与不可变正文；候选确认、并发冲突、来源变更可恢复 |
| 2 | VIEW、SCRIPT、SHOT、ASSET、REL、MEDIA | 真对象与准确版本；无限画布、阅读、高亮出线、共用资产 |
| 3 | JOB | 新对象任务，冻结输入、真实生成/审核/重试、队列定位 |
| 4 | EDIT | 真实视频资源、持久化剪辑、同版预览/导出/发布 |
| 5 | CHAT | 五步骤真实问答、历史、结构化提案与明确采用 |
| 6 | UI、GATE-01～05 | 新流程的数据、浏览器、任务、媒体、视觉先通过；旧代码尚待清除 |
| 7 | RETIRE | 按审定文件清单清除旧产品代码与入口，更新新运行说明 |
| 8 | GATE-06 | 旧代码依赖清除、实际运行基线和完整交付最终签收 |

各能力可以按依赖提前复验，但GATE-01～05必须先通过才清除旧代码；最后执行GATE-06。批次是组织方式，具体就绪以账本依赖为准。

可以先用明确隔离fixture建新UI，但不能作为业务接通的通过证据。内核或接口未接通，该能力就未完成；不再次将“前端写出”标为整体验收。

## 6. 测试、交付和返修规则

派发前核对当前目录的解释器与 Node 依赖，使用已安装运行时；不复制 .env 或真实数据库进 fixture。每个并行任务使用独立测试数据与输出目录。后端测试自带隔离数据根（`tests/studio/conftest.py` 建 `data/studio-test-*` 丢弃库）；启动真实服务器时显式给 `STUDIO_DATA_DIR`，不指向 `data/studio`。

```bash
# 在已固定的实施目录，测试文件创建后按任务运行
.venv/bin/python -m pytest tests/studio/test_fragments.py -q
node --test web/tests/studio/ranges.test.cjs
web/node_modules/.bin/tsc --noEmit -p web/tsconfig.json

# 批次集成/依赖变化/最终签收时
web/node_modules/.bin/next build
git diff --check
```

本机 `pnpm` 的 store 目录（`~/.local/share/pnpm/store`）不存在，`pnpm run …` 会以 ENOENT 失败；改用 `web/node_modules/.bin/` 下的 `tsc`/`next` 直调，二者与 pnpm 脚本等价。`node --test` 传目录参数在本机 Node 上会误报失败，须用通配符（`node --test 'web/tests/studio/*.test.cjs'`）或逐文件执行。

新增测试使用隔离数据库、媒体目录、假身份/供应商，确认不会指向生产数据。既有tests/conftest.py现在创建test-*目录；重构测试隔离设置要由主模型重新核对，不因为旧fixture能跑就绑定旧app业务。纯排版用主模型截图复验，不写镜像单测；业务边界、并发、状态丢失、版本、文件和历史必须有有意义的测试。

UI fixture只在隔离环境明确注入，不能进入普通项目。前端测试、后端测试、截图都记录受测commit/构建、端口和source/object/revision。没有浏览器证据的UI项保持未验证，不能“按库约束推断通过”。

返修闭环：

1. 主模型从全部依赖 accepted 的叶卡中挑选互不冲突的任务，逐项填写具体 schema、白名单、资源范围、步骤和负向案例后派发。
2. 执行器只报告submitted/blocked，附diff、命令退出码、观察和剩余项，停止；不自行接下一项或签accepted。
3. 主模型检查越界与业务含义，独立跑必要测试/浏览器；拒绝时写触发→实际→期望→准确目标→仅需修什么。
4. 两轮失败由主模型重新拆卡或亲自处理复杂点；契约改变升版本并标受影响任务，不能追加一堆提示让弱模型猜。
5. 通过后集成并绑定准确受测commit。每批回报已验收ID/实际效果/未通过项/下一项；只复查受影响路径，最后完整签收。

任务族已展开为带parent_id的单操作子卡；父卡只有全部子卡通过才accepted。主模型仍须在派发前填入冻结接口与收窄白名单。不得把退役大清单、所有分镜表单或所有来源命令一次扔给轻量模型。

后续任务按账本依赖和本节并行条件选择；未通过最终门槛不声明完整制作链路完成。旧台修补、业务交接和兼容迁移不再派发。
