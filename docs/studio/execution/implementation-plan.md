# Storyloom 全面重构原子实施与验收计划书

版本：2.1 · 2026-10-04。方向：**彻底重构，旧版本退役。** 状态：详细计划已编制，旧依赖盘点已完成，重构代码尚未开始。实际执行与验收见[任务账本](acceptance-ledger.json)。

本版为全面重构计划。根据用户最新决定，从已确认的设计建立新模型、新服务、新工作台和新生产/剪辑/对话链路，最终清除旧产品代码和入口。旧实现只供识别问题和可提取基础设施，不成为新流程约束。旧后端workflow、节点绑定、提示词契约及专用测试均退出标准；ROOT-02/04从当前产品规则重新定义新命令与生产/对话流程。

## 1. 最终交付及依据

一条真实、可恢复的路径：新建项目 → 导入原文 → 在连续阅读区划出荧光区域 → 保存候选/确认片段 → 剧本动作与对白 → 分镜与共用资产 → 生成/审核视频 → 左侧资源取用与全屏剪辑 → 确认同一剪辑版本 → 发布/导出。每步骤都有对象属性、实际任务状态和可恢复自然语言对话。

- 左侧原文/动态故事片段两视图；一个连续非空区域就是一个片段，候选和确认都不可重叠，允许相接。原文不插入片段卡片或状态。
- 切分、剧本、分镜、资产都是无限画布，自由拖动/平移/缩放；坐标不改变业务归属、顺序或版本。
- 剧本连线从整块高亮的实际边缘发出，一个起点和主干再分支到动作/对白。资产出现位置关联实际项目资产及版本，允许共用。
- 成片是占满主工作区的剪辑组件，左侧就是资源区；浏览/预览资源保留时间轴，明确插入产生独立实例。
- 属性对应选中的真实对象，步骤对话固定在工作区底部；不要求标出agent/model名称。

设计依据：[产品规范](../product/product-spec.md)、[确认稿](../prototypes/source-studio.html)。问题依据：[核对报告](../evidence/implementation-audit-2026-10-04.md)。技术依据：[项目结构](../architecture/project-structure.md)、[领域契约](../architecture/domain-contracts.md)。派发格式：[执行器提示词](executor-prompt.md)。

## 3. 执行方式与原子边界

主模型负责架构、schema/API/状态、内核、供应商/agent执行权、拆任务、审diff、独立复验、返修、集成和最终签收。轻量模型（如gpt-6-luna）只实现已就绪的一张卡。

默认串行：派一项 → 执行器submitted → 主模型验收 → accepted后再派后继。独立只读盘点/fixture可以并行；同文件、共享状态、依赖未通过的工作不并行。执行器不再派代理。

每卡一个明确行为，原则最多3个实现文件加直接相关测试。模型不能顺手完成整个工作区、猜接口、改变导航、加兼容/迁移、升级依赖或重排无关代码。白名单不足由主模型进一步拆卡。任务中指定多个状态只是同一行为的成功/失败面，不能用此扩张业务。

状态：`planned → ready → running → submitted → accepted`，失败为rejected，契约未定为blocked_by_design。ready必须由主模型确认具体接口已冻结、白名单已收窄且依赖已验收；任务族父卡不可直接派发。依赖只认主模型accepted；构建通过、按钮出现、执行器说完成都不能代替验收。账本由主模型维护。

## 6. 测试、交付和返修规则

ROOT-01选择实际解释器/Node依赖；当前主目录有`.venv/bin/python`和web/node_modules，文档工作树没有。可只读复用已安装运行时，不复制.env/真实数据库进fixture，不为计划提前安装依赖。

```bash
# 在已固定的实施目录，测试文件创建后按任务运行
.venv/bin/python -m pytest tests/studio/test_fragments.py -q
node --test web/tests/studio/ranges.test.cjs
pnpm --dir web typecheck

# 批次集成/依赖变化/最终签收时
pnpm --dir web build
git diff --check
```

新增测试使用隔离数据库、媒体目录、假身份/供应商，确认不会指向生产数据。既有tests/conftest.py现在创建test-*目录；重构测试隔离设置要由主模型重新核对，不因为旧fixture能跑就绑定旧app业务。纯排版用主模型截图复验，不写镜像单测；业务边界、并发、状态丢失、版本、文件和历史必须有有意义的测试。

UI fixture只在隔离环境明确注入，不能进入普通项目。前端测试、后端测试、截图都记录受测commit/构建、端口和source/object/revision。没有浏览器证据的UI项保持未验证，不能“按库约束推断通过”。

返修闭环：

1. 主模型挑全部依赖accepted的一张卡，填写模板中的具体schema/白名单/步骤/负向案例，派给轻量模型。
2. 执行器只报告submitted/blocked，附diff、命令退出码、观察和剩余项，停止；不自行接下一项或签accepted。
3. 主模型检查越界与业务含义，独立跑必要测试/浏览器；拒绝时写触发→实际→期望→准确目标→仅需修什么。
4. 两轮失败由主模型重新拆卡或亲自处理复杂点；契约改变升版本并标受影响任务，不能追加一堆提示让弱模型猜。
5. 通过后集成并绑定准确受测commit。每批回报已验收ID/实际效果/未通过项/下一项；只复查受影响路径，最后完整签收。

任务族已展开为带parent_id的单操作子卡；父卡只有全部子卡通过才accepted。主模型仍须在派发前填入冻结接口与收窄白名单。不得把退役大清单、所有分镜表单或所有来源命令一次扔给轻量模型。

本轮交付是完整计划、契约、执行提示词及账本；已经完成只读旧依赖盘点。下一步ROOT-01固定实施分支，然后主模型冻结新schema/API，执行器开始新模块建设。旧台修补、业务交接和兼容迁移不再派发。
