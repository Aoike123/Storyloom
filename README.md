## 快速启动

当前仓库提供免账号的本地 Demo。默认使用 SQLite，语言、生图和视频模型的付费调用均处于关闭状态。

### 环境要求

- Python 3.12+
- Node.js 20.9+
- pnpm 11.22.0
- Windows 一键启动需要 PowerShell

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
pnpm --dir web install --frozen-lockfile
pnpm --dir web build
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

启动脚本会在缺少配置文件时将 `.env.example` 复制为 `.env.local`，并初始化本地示意媒体。访问 <http://127.0.0.1:3000>；作者工作台位于 <http://127.0.0.1:3000/author>。

开发模式无需先构建前端：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start.ps1 -Dev
```

停止由脚本启动的进程：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/stop.ps1
```

不要重复运行启动脚本；需要重新启动时先停止已有实例。

### macOS 或 Linux 手动启动

安装依赖并初始化本地配置、示意媒体：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
pnpm --dir web install --frozen-lockfile
cp .env.example .env.local
python -m backend.media
```

随后分别在三个终端运行：

```bash
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
python -m backend.worker
pnpm --dir web dev
```

### PostgreSQL（可选）

本地开发默认不需要 PostgreSQL。如需验证 PostgreSQL 路径：

```powershell
docker compose up -d db
```

然后在 `.env.local` 中设置：

```dotenv
DATABASE_URL=postgresql+psycopg://story:story@127.0.0.1:5432/story
```

示例账号和密码仅供本机开发。现有 SQLite 数据不会自动迁移。

### 模型配置

可以在 `.env.local` 中填写自己的语言、生图和视频供应商配置。不要提交该文件，也不要在聊天、Issue 或日志中粘贴密钥。只有显式设置以下开关后，应用才允许真实付费调用：

```dotenv
ALLOW_PAID_CALLS=true
```

建议在功能开发、自动测试和公开演示中始终保持为 `false`。

### 验证

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
pnpm --dir web test
pnpm --dir web build
```

自动测试不会调用真实模型。

### 安全边界

当前版本没有账号、租户隔离或公共服务所需的限流与费用配额，只应在本机或受外部访问控制保护的演示环境中运行。请勿将端口 3000 或 8000 直接暴露到公网；参见 [安全策略](SECURITY.md)。

## 一 项目概述与创作思路

叙间是一款以知乎脑洞故事为内容起点的 AI 漫剧创作与互动阅读产品。我们希望让创作者把文字中的人物、规则和冲突拍成可观看的短场景，让读者在观看到某个情节时，可以用一句自然语言表达自己的选择。产品的长期目标是：保留已经发生的故事事实，生成与读者选择相符的局部剧情，并在条件允许时接回作者主线。

当前 Demo 已有知乎故事目录接入、脑洞题材导演编排、图片确认、视频制作、审片发布和播放流程的实现；读者端能够在暂停位置保存想法。自由改写后的真实视频分支生成与主线回归属于下一阶段目标，本计划书不将其描述为当前已完成的线上能力。

### 创作起点

我们从一个具体的阅读愿望出发：读到人物即将作出选择时，读者可能会想，“如果是我，我会怎么做？”脑洞故事尤其适合承载这种参与，因为它通常有一个偏离日常经验的设定，而人物行动必须回应这个设定。把选择及其后果表现出来，可以让讨论落到具体情境，而不止停留在一句评价。

文字转视频本身并不足以实现这一体验。如果只是把原文切成数段再分别生成画面，人物形象、世界规则、伏笔和因果容易失去关联。因此，叙间把故事理解、导演设计和素材管理放在生成之前，并保留人的审看与确认。

### 产品定位

叙间面向两类核心用户：希望把故事做成漫剧的知乎故事作者及获得相应授权的制作参与者，以及喜欢脑洞故事、愿意讨论人物选择的读者。创作端负责把可用正文转成短场景作品；读者端优先提供观看和表达想法的简单入口，不要求读者理解模型、分镜或制作参数。

首期聚焦脑洞类微小说的短场景，便于验证规则表达、人物反应和镜头连续性。后续再扩展悬疑、情感、幻想等题材，并按题材调整分析与审查步骤。

### 核心设计原则

- 原作可追溯。保留作者、来源、标签和改编范围，区分原文事实与改编设计。
- 作者可把关。风格、关键图片和成片由操作者确认，自动流程不等于自动认可作品质量。
- 选择有后果。互动设计保留已经接受的行动与角色记忆，不为复用原片而无解释地撤销选择。
- 生成有边界。只制作当前需要的片段；无法可信地接回主线时，说明冲突而非强行拼接。

## 二 适配知乎社区的场景价值

知乎内容在本项目中同时承担原作、讨论语境和叙事约束的作用。叙间围绕具体作品、作者与读者之间的关系组织体验，关注的是一段故事如何被理解、改编和讨论，而非脱离原作的通用视频生成。

### 场景一 让故事获得一种新的阅读入口

读者从脑洞故事目录选择作品，查看原文与署名；已有漫剧时，可以先观看对应短场景，再对照文字理解设定与人物。未制作的故事保留阅读和制作入口，不以空白成片或虚构热度充实目录。

短场景可以承担故事试读的作用：先呈现一个值得继续追问的设定或冲突，再让读者回到作品信息和原文。我们希望由此增加读者发现原作的机会。这个效果需要通过原文查看率等指标检验，目前没有转化率或用户增长数据。

### 场景二 把脑洞讨论定位到具体情节

读者暂停后留下“先保留证据再离开”“换一条路线试试”等想法，系统同时记录作品版本、镜头与时间点。相比脱离上下文的一句话，这种记录能明确读者在回应哪一幕，以及当时已经知道什么。

后续接入真实分支后，读者可以观看选择造成的后果，并与作者原版比较。讨论的问题会更具体：这个行动是否符合人物动机，是否违反故事规则，为何导致另一种后果。讨论质量与原作关联度比单纯增加生成数量更重要。社区内的分享和反馈回流属于后续产品规划，当前没有接入知乎评论或发帖接口。

### 场景三 降低故事作者尝试漫剧的制作负担

创作者选择故事后，可以从推荐风格或自己的描述开始，逐步确认人物与场景图片、查看分镜、审看视频并发布到应用内读者空间。AI 承担结构化分析和素材生成，创作者保留审美与叙事判断。

这条路径让作者有机会先用一个短场景检验“我的故事拍出来是否成立”，再决定是否扩大制作。角色、场景和镜头素材保留版本，也为后续局部调整提供基础。节省多少时间和费用，需要以同一故事的实际制作记录比较，不能以接口接通代替效果证明。

### 场景四 用原作约束维护内容归属

叙间将原始故事、AI 改编方案和读者提出的变体分别记录。读者的设想不自动变成原作者认可的剧情，AI 补充的设定也不反写成原文事实。面向社区扩展时，应由作者决定可参与的范围和是否展示读者版本。

我们预期形成的社区路径是：发现原作、观看改编、提出有情境的想法，再回到作品和作者展开讨论。当前已具备其中的故事导入、短场景制作和想法记录环节，其余环节按照授权范围与平台能力逐步验证。

## 三 产品体验与用户流程

### 创作者流程

1. 选择故事。从知乎故事目录进入制作页，读取所选正文并保留署名。打开原文不自动触发收费生成。
2. 确定风格。系统根据故事内容推荐三至五种风格，也允许创作者自由描述。风格建议与实际生成图片分别呈现。
3. 确认图片。制作人物、场景和必要的关键帧，检查外观、空间与道具；图片满意后再进入后续视频制作。
4. 审片发布。按镜头查看真实视频，选取实际使用区间，确认后形成发布版本，在应用内读者空间连续播放。

这些步骤背后包含故事分析、导演阐述、分镜、素材制作与任务调度。界面优先突出当前需要用户决定的事项，模型设置和维护工具放在次级入口。已完成的结果与正在等待的任务分别显示，页面关闭不会清空已保存的制作记录。

### 读者当前可以完成的体验

读者无需注册即可浏览 Demo 目录，优先看到已发布且媒体可用的作品。进入放映页后连续观看，在感兴趣的位置暂停并输入想法。系统保存原句与对应时间点，读者随后继续观看。

当前反馈明确表示“已记录创意，尚未生成或替换后续视频”。保存想法是一个已经落地的参与入口，也是未来真实分支所需的输入基础，但它本身不代表剧情已经改变。

### 下一阶段的互动目标

读者可以在观看中随时表达修改，不被限制为几个预设选项。系统根据暂停位置重建当前事实，判断意图与故事规则是否相容，生成必要的局部镜头，并寻找可兼容的原版后续。内部仍使用事件时间与合理剪辑边界管理衔接，“随时输入”不等于任何画面都能无缝切换。

如果读者在新片段中再次修改，系统保留已经看过的部分，只重新规划尚未播放的后续。对于与作者必要事实无法兼容的修改，应解释冲突并提供可行调整，而不是暗中抹掉读者刚刚做出的选择。

### 互动示例

以下是用于解释机制的原创示例，不代表某篇知乎原文。原版情节是“从正门进入，拿到钥匙，到地下室开门”。读者改为“翻窗进入再拿钥匙”，如果人物状态、钥匙归属和后续对白都兼容，就有机会复用地下室片段。

若读者改为“把钥匙烧掉”，则不能直接接回“掏出钥匙开门”。系统需要生成可信的其他开门过程、寻找更后的回归点，或提示当前无法衔接。回归主线保留的是必要的叙事连续性，不是把所有经历恢复成原样。

## 四 技术架构与知乎能力接入

叙间采用前后端分离架构。前端负责阅读、制作确认与播放；后端管理来源、作品和版本；独立执行器处理耗时的模型与媒体任务。生成结果先成为可检查的素材，再进入发布清单。

| 层级 | 技术与职责 |
| --- | --- |
| 用户界面 | Next.js、React、TypeScript，承载故事目录、创作流程、审片与读者播放。 |
| 业务服务 | FastAPI、Pydantic，管理故事导入、结构化方案校验、素材审核、发布版本与读者想法。 |
| 任务执行 | Python Worker 与持久任务记录，保存阶段结果、查询供应商任务、区分等待确认和执行失败。 |
| 数据与媒体 | SQLAlchemy 和本地 SQLite 保存记录；FFmpeg 处理媒体探测与剪辑，视频、图片及发布清单分别管理。 |
| 模型适配 | 分开接入语言、生图和视频服务。项目已有 DeepSeek、硅基流动生图、MiniMax 视频等适配路径，实际能力依所配模型验证。 |

### 知乎内容接入

当前使用赛事专用的故事列表和故事详情接口，能力边界为本次黑客松提供的内容，不将其描述为知乎全站内容库或长期稳定的通用接口。项目已保存列表与详情成功读取的核对记录。

列表入口为 GET /km-indep-home/hackathon/v2/story/list，详情入口为 GET /km-indep-home/hackathon/v2/story/{work_id}，请求域名为 api.zhihu.com。后端从列表取得作品标识，按需读取用户选中的正文；目录缓存、请求去重与明确的失效提示减少重复调用。

接入时保留 work_id、作者、原始标签、来源、获取时间和正文版本。正文完整性不能仅由字数判断：如果只能确认节选，制作范围就限定为该片段，不能凭空补出作者的完整结局。

当前 Demo 不依赖知乎账号登录，也未使用用户创作、关注、收藏等个人数据；没有接入热榜、直答、知识内容或向知乎发布的能力。无需为说明材料增加与现有产品无关的接口组合。

### 脑洞题材的导演编排

已实现的流程先提炼核心假设、规则与人物目标，再生成四至八镜的短场景分镜，随后进行单独一轮文本预审。分镜记录原文依据、主要动作、景别、角色和观众所知、铺垫关系、素材需求及入出状态。

程序检查原文引用能否定位、镜号是否唯一、揭示是否引用前序铺垫，以及剪辑时长是否超过生成素材。模型预审辅助判断因果与连续性；这些检查不等于成片视觉审核，最终画面仍由操作者验收。

## 五 核心技术设计与差异化

### 让故事规则进入制作流程

叙间将标签作为分析入口，再对照实际正文确认它如何影响叙事。脑洞流程重点处理假设、限制、代价和人物反应；后续的悬疑流程应检查线索与知情时间，情感流程应关注关系变化和动机。多个标签可以组合，但不能凌驾于原文事实之上。

由此，导演方案既影响画面风格，也影响分镜顺序和检查内容。未识别或相互矛盾的标签需要保留并说明不确定性。目前已落地脑洞主流程，其他题材专用流程仍待扩展与实测。

### 将作品保存为可复用的片段和版本

互动运行的核心载体是镜头、素材和播放清单，而非一条不可拆分的视频。项目已增加视频原文件保留、媒体属性与摘要记录、生成时图片快照、按实际帧选择剪辑区间，以及版本化发布清单，为局部替换提供基础。

一个镜头的叙事目的、一次模型生成的视频、最终选用的区间分别记录。已发布版本不随新一轮素材修改而原地覆盖。这样既能追查某段画面来自何次制作，也能在新版本中调整局部，而不破坏旧作品。

### 在条件允许时接回作者主线

真实互动阶段拟采用“局部改写加条件回归”的机制：从实际暂停位置重建事实，生成有限数量的新镜头，再复用能够承接这些事实的原版后续。

<!-- branch-figure -->

原版路径：已观看片段 → 原版中间片段 → 可兼容的回归点 → 原版后续

互动路径：已观看片段 → 读者改写片段 → 必要过渡 → 同一回归点

回归检查同时考虑剧情、视觉和时间。剧情包括人物知情、道具、关系与后续对白依赖；视觉包括服装、伤势、站位和场景；时间包括动作与对白是否真正完成。仅仅首尾画面相似，不足以证明能够衔接。

### 控制生成范围与等待

原版素材可被复用时，在线生成只覆盖当前选择所需的局部，不预先展开所有可能分支。首个新镜头完成必要检查后即可准备播放，后续镜头继续生成；必须依赖上一镜真实尾帧的任务则保留顺序依赖。

这属于逐段生成与播放的设计目标，不是已经验证的实时视频流能力。端到端等待还包含规划、模型排队、生成、下载和检查，不能用单一模型的推理时间代替用户看到剧情变化的时间。

### 与常见实现路径的取舍

相较于一次性全文转视频，本方案增加了导演结构、素材版本和审核成本，以换取可追溯与局部调整能力。相较于只提供预设选项的分支故事，自然语言参与更灵活，但必须承担意图理解和因果检查的难度。因此我们选择先验证一个短场景的可信互动，再扩展故事长度和输入范围。

### 当前能力范围

以下区分本地实现、原型验证和待完成目标。功能代码、本地流程测试与真实模型成片质量属于不同验收层次，不能相互替代。

| 正式运营与社区发布 | 当前为免账号共享 Demo，没有多用户隔离，也未接入向知乎发布；不作为生产环境直接开放。 |

### 第一阶段 完成可信的参赛演示

优先准备至少一个来源清楚、覆盖范围明确、经过人工审片的短场景。演示从故事与原文进入，展示风格和图片确认、成片发布，再由读者观看并保存想法。真实收费生成应事先完成必要的样片准备，评委观看不必等待整部作品制作。

提交前单独检查公网访问、视频文件可用性、首次播放、署名与范围提示，以及失败状态。公开演示应隔离制作与模型配置权限，避免任何访客都能改动作品或触发收费任务。代码已有实现不代表这些交付条件已完成验收。

### 第二阶段 验证真实互动闭环

选择单故事、少量角色、单一场景和少量回归点，先验证一次改写只生成一至三个必要镜头的路径。覆盖非预设时刻暂停、事实保留、局部视频生成、回归检查，以及在新片段中再次修改。不可回归、模型失败和旧任务迟到都纳入验收。

通过后再接入逐镜就绪的播放调度、素材复用和局部修复。完整配音、口型、音乐混音与统一单文件导出另行验证，不把分镜中的声音设计描述为已完成音轨制作。

### 第三阶段 扩展题材与社区参与

在已有流程质量稳定后，再增加题材专用导演流程、作者设定的参与边界，以及读者版本与原版的对照。只有在获得相应授权、具备身份与内容审核能力后，才考虑社区分享与反馈回流。

## 七 内容边界与验证方法

### 原作者与改编内容的关系

我们将保留作者与原作归属作为产品设计的前提。赛事接口能返回内容，不等于取得无限改编、商用或跨平台传播授权。参赛展示和后续运营分别核对使用范围；来源、AI 改编标识及实际覆盖片段应随作品展示，读者设想不冒充作者原意。

涉及真实人物或真实经历的内容，不应把虚构补充包装成事实。若未来扩展知识内容，也需要另行建立事实依据与核验流程，不直接套用虚构故事的自由改写机制。

### 生成和运行边界

原文、标签和读者输入都作为数据处理，不执行其中夹带的指令。模型输出经过结构与业务校验后才能驱动后续任务；敏感凭证由后端保存，不进入前端、分享材料或导出文件。

图片确认与成片审看保留人的判断。自动接受仅表示通过特定结构、引用或版本条件，不能被解释为视觉质量、内容安全或叙事合理性得到全面保证。

生成任务保存已知阶段和供应商任务编号，结果不确定时先核实，不盲目重复收费请求。用量按实际可得的文本 token、图片数量和视频生成记录呈现；费用未知时标为待核算，不以零元代替缺失数据。

当前免账号共享 Demo 不提供个人作品隔离。面向公开运营，需要补充身份权限、请求频率与费用约束、内容审核、数据清理和申诉处理。它们是上线条件，不是当前已交付能力。

### 用实际体验检验价值

下列指标用于后续样片测试和小规模用户研究，尚无可对外报告的达成数据。先建立基线，再决定改善目标；不以生成次数代替读者价值。

| 关注问题 | 记录与判断方法 |
| --- | --- |
| 读者能否顺利进入故事 | 记录首次播放成功率、到首帧的等待和观看完成情况；冷启动与缓存命中分开。 |
| 参与是否被正确理解 | 观察用户能否自行暂停、保存并继续，以及是否误以为当前已经生成新剧情。 |
| 改编是否帮助理解原作 | 记录原文查看行为，访谈读者能否说明核心规则、人物目标及改编范围。 |
| 作者是否能够控制结果 | 记录从选文到可用样片的耗时、人工修改点、废弃素材与审核退回原因。 |
| 真实互动是否可信 | 后续测量首次变化可见等待、改写意图实现情况、状态冲突、视觉衔接与回归失败。 |

### 项目目标

叙间希望验证一种适合知乎故事的参与方式：作者的文字被认真理解后成为可观看的场景，读者的想法被放回具体情境，并在清楚的创作边界内探索另一种行动。首期以可追溯的短场景制作和想法记录建立基础，逐步实现真正可观看、保留因果的互动分支。
